# Requirements: Real-Time Streaming Optimizations

## Overview
Transform the WebRTC-based bilingual chatroom to provide near-instantaneous transcript and audio streaming, creating a natural conversation experience with minimal latency.

## Business Goals
- Reduce perceived latency from ~1-2 seconds to ~200-400ms
- Provide real-time visual feedback during translation
- Create a phone call-like natural conversation experience
- Improve user engagement through responsive UI

## User Stories

### US-1: Word-by-Word Transcript Streaming
**As a** chatroom participant  
**I want to** see the other person's words appear in real-time as they speak  
**So that** I can follow the conversation naturally without waiting for complete sentences

**Acceptance Criteria:**
- AC-1.1: Each word appears on screen within 100ms of being spoken
- AC-1.2: Words append progressively to the current message bubble
- AC-1.3: Partial transcripts update smoothly without flickering
- AC-1.4: Complete sentences are finalized and stored in chat history
- AC-1.5: Transcript streaming works for both English and French participants

### US-2: Streaming Audio Translation
**As a** chatroom participant  
**I want to** hear the translation audio as it's being generated  
**So that** I don't have to wait for the complete translation before hearing anything

**Acceptance Criteria:**
- AC-2.1: Audio chunks play as soon as they're generated by OpenAI
- AC-2.2: Audio uses the "ballad" voice for all TTS output
- AC-2.3: Speaker does NOT hear their own translated audio
- AC-2.4: Recipient hears audio with <400ms latency from when speaker finishes
- AC-2.5: Audio chunks play smoothly without gaps or stuttering
- AC-2.6: Existing muting logic prevents echo during push-to-talk

### US-3: Translation Progress Indicator
**As a** chatroom participant  
**I want to** see an immediate indicator when the other person starts speaking  
**So that** I know translation is in progress before words appear

**Acceptance Criteria:**
- AC-3.1: "Translating..." indicator appears within 50ms of voice activity detection
- AC-3.2: Indicator disappears when first transcript word arrives
- AC-3.3: Indicator is visually similar to WhatsApp's typing indicator
- AC-3.4: Indicator doesn't interfere with existing chat messages
- AC-3.5: Multiple rapid speech events don't cause indicator flickering

### US-4: Optimized Architecture
**As a** system architect  
**I want** a single-pipeline architecture with minimal server processing  
**So that** latency is minimized and system resources are optimized

**Acceptance Criteria:**
- AC-4.1: Pipeline follows: Speaker Mic → WebRTC → OpenAI Realtime API → Recipient
- AC-4.2: Server only relays messages, doesn't re-process audio or transcripts
- AC-4.3: SPEECH_TRANSCRIPT events carry partial/incremental transcript data
- AC-4.4: BILINGUAL_MESSAGE events carry streaming translation chunks
- AC-4.5: Existing deduplication logic in useChatroomConnection.ts is maintained
- AC-4.6: Dynamic muting (setAudioMuted) continues to prevent echo

## Functional Requirements

### FR-1: Incremental Transcript Capture
- System MUST capture partial transcripts from OpenAI Realtime API streaming events
- System MUST distinguish between partial and final transcript events
- System MUST handle transcript updates for the same utterance
- System MUST preserve transcript ordering across network delays

### FR-2: Progressive UI Updates
- UI MUST update transcript display on every new word received
- UI MUST append words to existing message bubble during streaming
- UI MUST finalize message bubble when utterance completes
- UI MUST handle rapid successive updates without performance degradation

### FR-3: Audio Chunk Streaming
- System MUST stream audio chunks as they're generated by OpenAI
- System MUST queue and play audio chunks in correct order
- System MUST handle audio chunk boundaries smoothly
- System MUST use "ballad" voice for all TTS generation

### FR-4: Voice Activity Detection
- System MUST detect when speaker starts talking
- System MUST trigger "translating..." indicator immediately
- System MUST detect when speaker stops talking
- System MUST clear indicator when transcript streaming begins

### FR-5: Message Routing
- System MUST route partial transcripts only to recipient (not speaker)
- System MUST route audio chunks only to recipient (not speaker)
- System MUST maintain existing participant ID logic
- System MUST prevent audio echo through proper muting

## Non-Functional Requirements

### NFR-1: Performance
- End-to-end latency MUST be ≤400ms for 95th percentile
- Transcript word display latency MUST be ≤100ms
- Audio chunk playback latency MUST be ≤200ms
- UI updates MUST maintain 60fps during streaming

### NFR-2: Reliability
- System MUST handle network jitter gracefully
- System MUST recover from dropped packets
- System MUST handle out-of-order message delivery
- System MUST maintain message integrity during streaming

### NFR-3: Compatibility
- Solution MUST work with existing WebRTC infrastructure
- Solution MUST work with OpenAI Realtime API constraints
- Solution MUST maintain backward compatibility with existing message format
- Solution MUST work on both desktop and mobile browsers

### NFR-4: Maintainability
- Code MUST follow existing project patterns
- Changes MUST be isolated to relevant hooks and components
- Logging MUST provide visibility into streaming behavior
- Error handling MUST be comprehensive and informative

## Technical Constraints

### TC-1: OpenAI Realtime API
- Must use OpenAI's streaming transcription events
- Must handle partial transcript updates
- Must use "ballad" voice for TTS
- Must work within API rate limits

### TC-2: WebRTC
- Must maintain existing WebRTC connection
- Must not introduce additional audio channels
- Must preserve existing muting logic
- Must handle browser-specific WebRTC behaviors

### TC-3: WebSocket Server
- Server must only relay, not process
- Server must maintain low latency
- Server must handle concurrent connections
- Server must preserve message ordering

### TC-4: React Frontend
- Must use existing hooks pattern
- Must maintain component separation
- Must avoid unnecessary re-renders
- Must handle state updates efficiently

## Out of Scope
- Video streaming
- Group chatrooms (>2 participants)
- Recording/playback of streaming sessions
- Language detection (English/French only)
- Custom voice selection beyond "ballad"
- Offline mode or caching

## Success Metrics
- Average end-to-end latency: <300ms
- 95th percentile latency: <400ms
- User-perceived responsiveness: "instant" feedback
- Audio quality: No stuttering or gaps
- Transcript accuracy: Matches OpenAI API output
- System stability: No crashes or freezes during streaming

## Dependencies
- OpenAI Realtime API availability
- WebRTC browser support
- WebSocket server stability
- Network bandwidth: Minimum 100kbps per participant

## Risks and Mitigations

### Risk 1: Network Latency
**Impact:** High  
**Probability:** Medium  
**Mitigation:** Implement adaptive buffering, graceful degradation

### Risk 2: OpenAI API Rate Limits
**Impact:** High  
**Probability:** Low  
**Mitigation:** Monitor usage, implement backoff strategy

### Risk 3: Browser Compatibility
**Impact:** Medium  
**Probability:** Medium  
**Mitigation:** Test on major browsers, provide fallback for unsupported features

### Risk 4: Audio Chunk Synchronization
**Impact:** Medium  
**Probability:** Medium  
**Mitigation:** Implement robust queuing and ordering logic

## Correctness Properties

### CP-1: Transcript Ordering
**Property:** For any sequence of words W1, W2, ..., Wn spoken by a participant, the recipient MUST see them displayed in the same order W1, W2, ..., Wn.

**Test Strategy:** Property-based test generating random word sequences and verifying display order matches input order.

### CP-2: Audio-Transcript Synchronization
**Property:** For any utterance U with transcript T and audio A, if T is displayed to recipient, then A MUST be played to recipient within 500ms.

**Test Strategy:** Property-based test measuring time delta between transcript display and audio playback start.

### CP-3: Speaker Isolation
**Property:** For any message M generated by participant P, participant P MUST NOT hear the translated audio of M.

**Test Strategy:** Property-based test verifying audio routing never sends translated audio back to originating participant.

### CP-4: Message Completeness
**Property:** For any complete utterance U, the final displayed transcript MUST contain all words from U without omissions or duplications.

**Test Strategy:** Property-based test comparing final transcript against source utterance for completeness and uniqueness.

### CP-5: Indicator Timing
**Property:** For any voice activity event V, the "translating..." indicator MUST appear before the first transcript word is displayed.

**Test Strategy:** Property-based test verifying indicator timestamp < first word timestamp for all utterances.

## Assumptions
- Participants have stable internet connection (>100kbps)
- Participants use modern browsers with WebRTC support
- OpenAI Realtime API maintains current streaming capabilities
- Server has sufficient capacity for message relay
- Participants speak clearly enough for accurate transcription
